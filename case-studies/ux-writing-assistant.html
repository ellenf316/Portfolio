Innovaccer AI UX Writing Assistant

Building a custom Claude Project trained on Innovaccer's UX writing style guide, so any product designer, PM, or engineer can draft and review UX copy to the same standard — without a content designer in the room.

Company
Innovaccer
Tool
Custom Claude Project
Role
Lead Conversation & Content Designer

Challenge

I was the only content designer at Innovaccer — but product designers, PMs, and engineers across the company were all writing UX copy: button labels, error messages, empty states, AI-agent dialogue. Without a scalable way to apply our style guide consistently, copy quality varied screen to screen, and inconsistencies piled up across files that I alone had no way to catch in time.

I built a custom Claude Project — a UX writing assistant trained on our style guide — so anyone on the team could draft or review copy against the same standard I'd apply myself, without waiting on content design to be available.

Building the Foundation: The Style Guide

Before the assistant could enforce anything, the standard itself had to exist in a form a model — and a human — could actually apply. I wrote a UX writing style guide covering Innovaccer's house style, accessibility and localization requirements, voice and tone (including a dedicated persona layer for Sara, our AI medical-receptionist agent), and a library of content patterns by UI element, each with concrete right and wrong examples:

Buttons

✓Save draft · View details · Download report · Finish intake
✕Click This Button to Proceed to the Next Step · Submit · Done · Go

Confirmation Messages

✓Your request has been sent. · Medication order submitted. View summary or place another order.
✕Success! · Done. · You did it! · Yay! All finished.

AI Buttons

✓Summarize notes · Suggest diagnosis · Draft response with AI · Analyze vitals
✕Let AI Write · Diagnose patient · Start AI · Answer for me

That last category matters more than it looks: the guide is explicit that AI buttons should never imply the AI is making a final decision — "Suggest diagnosis," never "Diagnose patient." Positioning AI as a helpful assistant rather than an authority runs through the whole guide, not just the AI-specific sections.

The Assistant Itself

The style guide became project knowledge; the instructions turn it into an active reviewer. The project's system prompt tells Claude exactly what to check for, how to cite the guide when flagging a violation, when to switch into Sara's persona voice versus general UI copy, and — critically — to track consistency across files, not just within a single screen.

Project Instructions

You are a UX writing assistant for Innovaccer, a healthcare technology company. Your job is to help product designers, writers, and PMs draft and review UX copy so it's consistent with Innovaccer's UX Writing Style Guide (attached as project knowledge).

Most of what you'll review is plain UI copy — buttons, headings, error messages, empty states, toasts, tooltips, form labels, etc. A smaller portion is copy spoken as Sara, our AI medical-receptionist agent, which follows an additional persona layer on top of the base style rules. Don't assume every request involves Sara — default to general UI copy unless the user says otherwise or the context makes clear it's an AI-agent-facing message.

Core responsibilities

  1. Draft new UX copy when given a description of the screen, user goal, or context — or a Figma file/frame to reference directly.
  2. Review and edit existing copy, flagging anything that violates the style guide and explaining why, citing the specific rule.
  3. When working from Figma, reference the actual frame/screen content rather than guessing.
  4. Track copy consistency across files — flag inconsistent terminology or patterns between screens (e.g., one says "ER," another says "ED") even if no single instance violates the guide on its own.
  5. Write copy for Sara specifically when the request calls for it, following her voice and tone guidelines.

When reviewing copy

  • Point out specific violations with the relevant guide section.
  • Suggest 1–2 alternative options, not just one, when there's room for voice/tone judgment.
  • If copy breaks a pattern but arguably serves the user better, say so rather than forcing a rigid fix.
  • When reviewing across multiple files, call out cross-file inconsistencies as their own category of feedback.

Seeing It Work: A Quick Fix

A teammate pasted a screenshot of an existing password error message and asked for a rewrite. The assistant didn't just reword it — it flagged why the current version violated the guide, cross-referenced an existing error-message pattern library to keep the fix consistent with other errors already shipped, and offered a second, slightly more explicit alternative.

Prompt: [pasted screenshot above] — "rewrite this"

Issues vs. style guide

  • "You've got" — contraction reads casual/colloquial; guide favors plain, direct phrasing over idiom-adjacent language.
  • "just click on 'Forgot password'" — "click on" is directional/informal language the guide flags (avoid "click here" type phrasing); "just" is filler.
  • This also has an existing pattern in the Error Messages sheet ("Incorrect password / 4 attempts left. Try again. / Forgot password?") that this version doesn't match — worth aligning for consistency.

Rewrite (matches existing pattern)

⚠ Incorrect password
4 attempts left. Try again.
[Forgot password?]

Alternative (slightly more explicit)

⚠ Your password is incorrect
You have 4 attempts left. Try again, or reset your password.
[Forgot password?]

Either works — first option matches your documented pattern exactly, so I'd default to that for consistency unless there's a reason this screen needs more context.

Seeing It Work: A Full Screen Audit

To stress-test the assistant on something bigger than a single string, I built Careflow — a mockup care-gap workflow tool — deliberately seeded with the kinds of copy issues that creep into real products: title-case headings, vague buttons, missing field labels, generic error text. I dropped all four screens into the assistant with a single prompt: "here you go." It thought for 40 seconds and returned a full audit, screen by screen, plus a cross-screen consistency section catching patterns no single-screen review would surface.

Cross-Screen Consistency

These issues span multiple screens and should be fixed as shared patterns, not one-off edits per screen:

  • Heading case is inconsistent everywhere, not just per screen — "Care Gap Worklist," "Active Care Plan," and "You Have Notifications" all use title case. Standardize to sentence case app-wide.
  • Primary action buttons use three different, all-vague verbs for essentially "confirm/start" actions: "Initiate," "Submit," "Go." Converge on a shared, specific action + object pattern.
  • Label pattern is missing app-wide, not just once — both the Care Plan form and the Assign modal rely on placeholder text with no real field label.
  • "MRN," "DOB," and "PCP" are standard clinical shorthand appropriate for this clinician-facing tool — no change needed.

Iterating With the Team

The assistant didn't ship once and stay static. Once product managers, designers, and engineers started using it directly, they came back with feedback — places where it was too rigid, guide sections that needed clarifying, edge cases the instructions didn't cover. I kept updating the project's instructions and the underlying style guide as that feedback came in, so the assistant got more accurate the more the team actually used it.

Results

Heavily adopted across teams. Product managers, product designers, and engineers at Innovaccer use the assistant directly — not just people with content design backgrounds.

Minutes, not a queue. A full four-screen audit that would otherwise wait on content design's availability came back in under a minute, catching both single-screen and cross-screen issues.

Consistency at scale. Cross-file pattern-matching (inconsistent CTA verbs, mismatched terminology) catches issues a single-screen review would miss entirely.

Handoff-ready by default. The assistant can turn its own audit into a clean before/after reference doc, ready to hand to a design team without extra formatting work.
